# Original sound heap execution checkpoint

The original sound/frame allocator executes successfully in the provider harness.
Canonical integration is **not implemented**; the existing executable still faults
inside `NNSi_FndInitHeapHead`. No compiler, production provider or upstream source
was changed by this checkpoint.

## Reproduction

Use the configured LLVM tools and `guest32-lower` target from the selected build:

```sh
python3 -B tests/provider_software_execution.py --build build \
  --llvm-bin "$LLVM_BIN" \
  --lowerer build/guest32-compiler/guest32-lower
```

Set `LLVM_BIN` to the configured LLVM tools directory.
The harness writes commands and results to `build/provider-experiments/`.
`sound-heap-execution` runs at O0/O2, with and without ASan/UBSan. Each runs
both guest-owned RAM and an externally owned native buffer, then a separate
invalid-address process. The pre-existing heap, stream, scalar and VCT matrices
remain enabled: twenty positive matrix entries in total.

## Original providers and ABI

Original complete `snd_heap.c`, `fnd_frameheap.c`, `fnd_heapcommon.c` and
`fnd_list.c` are lowered together. Additional original entries are `arith.c:abs`,
`snd_player.c:NNS_SndPlayerCreateHeap/PlayerHeapDisposeCallback`, and
`snd_arc.c:InfoDisposeCallback/FatDisposeCallback/SymbolDisposeCallback`.
The existing MI guest provider supplies clear operations. The fixture observes
the original `EraseSync` command-tag/flush/wait protocol using test-only transport
functions; this does not test actual SDK command processing or audio output.
No frontend or lowering changes were necessary.

Compile-time layout checks and an original `sound.c` ARM32 layout dump establish:

| Structure | Size | Selected offsets |
| --- | ---: | --- |
| SND_WORK | 781448 | heap 148, heap_buf 152 |
| NNSSndArc | 148 | fat 132, symbol 136, info 140 |
| NNSSndHeap | 16 | frmHeap 0, sectionList 4 |
| FrameHeap | 48 | frame 36 |
| FrameHeapState | 16 | tag/head/tail/prev are four words |
| SndHeapBlock | 32 | callback 12, data1 16 |
| SndHeapSection | 20 | blockList 0 |
| SndPlayerHeap | 20 | buffer 20 |

These guest structures use four-byte alignment and original pointer words.
`0xBEAE0` is **781024**, not 780000. No capacity constant was changed.

Original callbacks keep `void(void *, u32, u32, u32)`. Generated guest entries
take the arena followed by four 32-bit guest/scalar arguments. The original
typed indirect dispatcher selects code identities; no native function-pointer
cast is used. Archive callbacks decode `data1` through original guest operations;
other observed words include `0xffffffff` and `0xfedcba98` unchanged.

The fixture checks frame head/tail allocation, state rollback, exact capacity,
exhaustion, sound payload alignment, requested sizes, allocation order, section
rollback, reverse disposal order and arguments, original player subheap cleanup,
archive pointer clearing, and restoration of initial capacity. Canary bytes
surround the supplied region. Host addresses exceed 4 GiB. The native-buffer
variant uses `g32_borrow_native_bytes`, `g32_resolve`, `g32_encode` and unbinding:
one buffer, no payload copy, including an interior alias. This is isolated test
ownership evidence, not a mapping installed over canonical `sSoundWork`.

## Canonical evidence and remaining boundary

`build/dynamic-closure/canonical/link.map` selects native `sound.c` storage and
native `snd_heap.c`/`fnd_frameheap.c` from
`final-closure/ds-memory-lowering/libheartgold_main_native_ram.a`.
LLDB measured the following, with logs beside that executable:

- `sound-heap-lldb.log`: sound creation receives `0x10041e560`, native
  `sSoundWork + 240`, size `0xBEAE0`.
- `sound-frame-heap-lldb.log`: frame creation receives `0x10041e580`, size
  `0xBEAC0`; heap-header initialization subsequently writes `FRMH` through
  `0x0041e580`. This proves truncation inside the native frame-heap path.
- The stack is `NitroMain → InitSoundData → NNS_SndHeapCreate →
  NNS_FndCreateFrmHeapEx → InitFrameHeap → NNSi_FndInitHeapHead`.

The dynamic closure audit still finds 120 application images, 19419 strong
application import edges and zero missing imports; see
`build/sound-heap-dynamic-closure.json`. This is an audit of the existing
executable, not a newly integrated link or a fresh 805-member compilation count.
Seven selected CTest regressions pass, including sound data/storage, original
callbacks and their build dependency, native provider registry, guest32 regression
and guest32 bridge; see `build/sound-heap-regressions.log`.

`cmake --build build --target heartgold -j8` was also run to completion. It
rebuilds the main archive, native overlays and guest provider closure, then fails
at the executable linker with 22 unresolved symbols. The actual linker-derived
inventory is `build/sound-heap-canonical-build-symbols.tsv`, generated by
`cmake/link_symbols.py`; the full log is `build/sound-heap-canonical-build.log`.
No replacement canonical executable was produced by that build.

The remaining invariant is representation agreement across the native/guest
sound boundary. `native_sources.py` currently widens native callback payloads to
`uintptr_t` and enlarges/aligns native sound blocks. Native `NNSSndArc` embeds
native `FSFile`; `SND_WORK` therefore has a different buffer offset. The tested
guest allocators cannot replace their native symbols while native consumers
continue to dereference these metadata layouts or store native callbacks.
Existing typed-range code fields require a proven callback adapter; the byte
mapping alone does not supply it.
The canonical map also selects native ExpHeap/common/list providers and a
24-byte native `gFndRootHeapList`. Guest sound heaps must not silently acquire a
second registry that loses containment relationships with existing native heaps.
The isolated fixture's private root list does not establish canonical registry
agreement, and its passing ExpHeap regression does not authorize migrating
canonical ExpHeap.

The next implementation step is to bind the sole existing heap buffer and admit
an explicitly typed sound boundary covering handles, native archive ownership,
callback code identities and callback-specific pointer/scalar arguments, or move
those consumers together into the original guest representation. Preserve the
working native providers until that boundary is established. The next canonical
execution milestone is return from `NNS_SndHeapCreate` followed by entry into
`NNS_SndArcInit`; neither milestone is established here.
